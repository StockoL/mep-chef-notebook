# Decisions

## Settled

| # | Decision | Why |
| --- | --- | --- |
| 1 | Local-first PWA; the chef owns their data; no central server or accounts | Chefs move between kitchens; kitchen signal is poor; data shouldn't depend on a service |
| 2 | Open, documented export/import, available from the first usable build | The device holds the only copy |
| 3 | Rules-based step parser at the core, not AI | Offline, consistent, explainable, testable |
| 4 | Three step modes: active, check-in, passive | Active/passive alone misplaces reductions, skimming, sweating |
| 5 | Each variation is draft or ready; drafts never go into the automatic plan | A plan must never be quietly wrong |
| 6 | Scheduling algorithm is swappable; greedy is a baseline only | Better approaches may exist; the step data is what's fixed |
| 7 | Active timings belong to the chef; passive timings belong to a kitchen's equipment | Knife speed travels, oven quirks don't |
| 8 | Kitchens are switchable profiles; "no kitchen" is valid; Home is a kitchen | Agency and relief chefs; home cooking |
| 9 | Replaced by 17 (purposes are now suggested tags) | |
| 10 | Fewest taps during a shift; setup may ask for more | Data quality at setup makes everything else work |
| 11 | Free and open source; optional donations; no chef subscription | Chefs already give enough to the job |
| 12 | UI built on LooseLeaf-UI, installed from its published npm package (name and version as in the looseleaf-ui repo's package.json) | Louis's own toolkit; the Django package doesn't apply to a client-only app |
| 13 | Stack: Vite + TypeScript (strict), Preact, Dexie.js over IndexedDB, vite-plugin-pwa (Workbox), Vitest | Local-first means all logic runs in the browser; types guard the parser and scheduler; Dexie gives versioned migrations; Preact handles live timers and re-sequencing; Vitest shares Vite's config |
| 14 | Export format: a single `.zip` with `data.json` + media files | Photos and voice notes don't belong inside JSON |
| 15 | Built from one chef's view: what they do, know and are responsible for; never tracks other chefs or the whole kitchen | A commis can't see the whole kitchen, and an app that pretends to would be wrong and intrusive |
| 16 | Every list is editable (rename, reorder, merge, hide, add); seeded values are defaults only. Fixed: the 14 allergens, units, the three step modes | Kitchens name things differently; the app mustn't dictate "Larder" to a kitchen that says "Starters" |
| 17 | Building blocks are dishes (anything served), components (a recipe for one part) and ingredients (basic or bought-in). Purposes are suggested tags, never fixed categories | "Recipe" meant two things; a starter can become a main |
| 18 | Status, kitchen and source live on the variation, not the component; shelf life lives only in kitchen house rules | One stock can be ready in one kitchen and a draft in another |
| 19 | The plan is the shift sheet in time order, not a second list | Two lists drift apart |
| 20 | Phase 0 creates the whole v1 schema, including tables whose screens come later | Real data arrives from Phase 1; breaking migrations on a chef's only copy are a risk |
| 21 | On iPhone it ships as a home-screen web app (Safari → Share → Add to Home Screen), not through the App Store. First run teaches the install step. An App Store wrapper (e.g. Capacitor) stays possible later from the same code | Own icon, full screen, offline and better storage protection without Apple review or a paid developer account; iPhone never prompts to install, so the app must show how |
| 22 | Name: **Mep**, with the descriptor "chef's notebook and prep planner". Manifest `name` "Mep: chef's notebook and prep planner", `short_name` "Mep" | How UK kitchens say MEP, as a word; no rank, so it still fits at CDP or sous; the descriptor makes it findable despite the political meaning |
| 23 | Load LooseLeaf's CSS and `theme.js`, not `looseleaf.js`; behaviours (tabs, toasts, menus) are Preact components using LooseLeaf's markup; sheets are native `<dialog>` | `looseleaf.js` edits existing HTML, and Preact expects to own what it renders; two owners means hard-to-trace bugs |
| 24 | Theme in `design/design-tokens.json` (LooseLeaf configurator): fluid 360–1024 px, 17 px body, system fonts, burnt-orange action, red danger kept apart from it. Details in docs/DESIGN.md | Phone-first, offline from the first open, arm's-length reading, colours that can't be confused |
| 25 | No reliance on haptics; vibration only where supported (Android) | Safari on iPhone has no vibration API |
| 26 | Text size follows the phone (`font: -apple-system-body` on iOS, the browser setting elsewhere); no in-app size control; layouts must work at the largest accessibility sizes | Don't fight Apple: the chef has already chosen a size for every app on their phone |
| 27 | Permanent address: GitHub Pages, public repo, at `/mep-chef-notebook/` (Vite `base`, used in dev too). Phone testing in dev uses mkcert for HTTPS | IndexedDB data belongs to the origin, so the install address must never change; service workers and `crypto.randomUUID()` need a secure context |
| 28 | Every row's id is a string UUID from `crypto.randomUUID()`, with `createdAt` and `updatedAt` | Import, sharing and any later sync never clash, unlike auto-numbered ids |
| 29 | Schema v1 adds two tables to SPEC's list: `media` (photo and voice Blobs, referenced by id) and `settings` (key/value: last kitchen and section, persist result, last backup, theme) | Blobs stay out of the data rows and map straight onto the export's `media/` folder |
| 30 | "No kitchen" is a real Kitchen record with id `"none"` (name "No kitchen", can't be deleted), created on first run. A `kitchenId` that means "where I am" is never null. `null` means only "not tied to any kitchen" (own, book and idea variations, techniques, ingredients) | IndexedDB can't index null, so compound indexes and "no kitchen" queries work; the two meanings stay apart |
| 31 | Ship first, learn later: the app is built for use on shift as soon as possible; learning the stack comes afterwards, from the phase log. Tests, versioned migrations and the export round trip stay, because they protect the chef's only copy | Louis needs the app now; the safeguards cost little and a lost notebook can't be undone |
| 32 | A service is one row (name, order, hidden, "I work this") holding a list of time windows, each for given days. SPEC's flat service fields became `windows` in schema v2 | Times differ by day (Sunday lunch runs later); renaming, hiding and reordering a service must act on one thing |
| 33 | Captured photos are saved as JPEG with the long edge at most 2000 px | Phone photos are 3–5 MB; the phone holds everything and every backup carries it |
| 34 | The fixed units are g, kg, ml, l, each, portion, plus kitchen count words: tsp, tbsp, pinch, bunch, sprig, clove, slice, sheet, leaf, tin, pack, dash, splash, handful, knob, smidgen, glug, dollop, and pint (shown as written, measured as 568 ml; added 25 Nov 2026). Metric and pints convert within weight or volume; count words never convert. cl and dl are read and stored as ml. A unit written without a number ("turmeric pinch", "half pint lager") is read as one (or a half) | Chefs write "thyme 3 sprigs"; forcing grams loses meaning, and a free-text unit can't be scaled |
| 35 | A sheet keeps the photo of chef's paper sheet it was entered from (`Sheet.photoId`, schema v3) | So the original can be checked later |
| 36 | "Today" for the sheet is the calendar date; it rolls over at midnight | Simple and predictable; a late finish can still open yesterday's sheet from the sheet list |
| 37 | *Replaced by 48.* Covering two sections: the usual section switch stays 2 taps, and "Also covering" in Where are you today? adds a second. Both share one sheet (`Sheet.sectionIds`) | MS3 without slowing the common switch |
| 38 | A written method line is one `Step`; the step reader stores the pieces of work it found in it as `Step.parts` (schema v4). The chef's text is never rewritten; the planner schedules parts | Splitting into separate lines would change the chef's text under them as they type |
| 39 | Draft or ready is worked out from the steps, never set by hand: every step confirmed, every part with a mode and a time, and check-in and passive parts with equipment. A part done to order needs no time; a part that is only a hold ("holds 3 days") needs nothing. No method = draft | A plan must never be quietly wrong (DECISIONS 5); service work isn't prep |
| 40 | A correction to a part's kind or equipment teaches the word list for that part's verb, at once, with Undo; time and setting corrections stay with the recipe. "Bench" joins the equipment list for work done by hand | Learning the word is P2; Undo covers one-off exceptions ("these nuts burn: check-in") |
| 41 | Rough amounts (pinch, smidgen, dash, splash, glug, dollop) are stored as written, never as numbers. From Phase 5, a scaled amount of one shows an estimate beside it, marked ≈, from a fixed table: smidgen ≈ 1/32 tsp, pinch ≈ 1/8 tsp, dash ≈ 1/8 tsp, splash ≈ 1 tsp, glug ≈ 2 tbsp, dollop ≈ 1 tbsp ("10 pinches (≈ 1 tsp)"). Knob and handful get no fixed estimate; an ingredient can carry the chef's own ("my handful of parsley = 40g"). Estimates are never used for costing or allergens | A pinch at normal size is how it's made; scaled ×10 it needs a measure. Handfuls vary too much by ingredient to share one figure |
| 42 | Scaled amounts round to what can be measured: weight and volume to 0.5 under 10, 1 under 100, 5 under 1000, then kg or l to 10 g/ml; pints to ¼; tsp to ¼, tbsp to ½; each to ½ under 5, else whole; portions whole; pinches, sprigs and other counts to ½ under 3, else whole. Nothing rounds away to nothing. Spoons and counts show as fractions (1½ tsp) | Kitchen scales weigh to the gram; nobody measures 0.37 of a sprig |
| 43 | The last scaling choice is remembered per component (and portions per dish) in settings, shown by a banner that can't be missed. While scaled, the scaled list replaces the ingredients editor; the recipe is only edited as written. Headcount is portions: a dish scales by "covers or people" through each component's amount per portion. The chef's own weights live on the ingredient (`Ingredient.unitWeights`, schema v5) | UX rule 2 without risking a scaled recipe being mistaken for the real one, or edited by accident |
| 44 | A recipe learned in a kitchen the chef has left is that kitchen's house recipe; the kitchen is kept as archived ("left"). Changing a recipe's origin moves its steps' equipment to the new kitchen's list by name. "On the day before service" is the same day; bowls and hand whisks are work by hand (Bench), and the step reader also reads the kitchen's own equipment names | The recipe book follows the chef between jobs (SPEC); attribution shouldn't need a fake book entry |
| 45 | A version is one editing session: ingredient and method edits within 30 minutes of the last go into the current version; after a break, the next edit starts a new version copied from it. Step-reading corrections and confirmations change the current version in place. Restoring copies the old version into a new current one (undoable) | "Every edit makes a version" without a version per keystroke; history stays readable |
| 46 | The variation in use is worked out (this kitchen's house recipe, then the chef's own, then any), never picked; the chips under a component's name only choose which one is shown, and say when it isn't the one in use. A copied variation's steps start unconfirmed | Downstream (sheet, plan, scaling) must not change because the chef looked at another version |
| 47 | Menus: a new menu starts on now; a copy starts coming up; launching sets it on now from today and moves the menus it replaces to past. A section's list is what the chef added (standing items, pars) plus every component the menus on now assign to that section; giving one a par makes it a stored item. Dish allergens are gathered from recorded ingredients only until food safety (Phase 10) | Changeover in a few taps; a new menu updates the section list by itself |
| 48 | The app doesn't ask which section the chef is on (replaces 37 and the usual section). The current place is the kitchen only, switched from ••• → Kitchen. Today's sheet is the kitchen's sheet for the day (new sheets have no sections; older ones still open). Sections stay for what's kitchen data: which section makes each component on a menu, section lists with pars, and filters; a section's list is picked with a chip and the last one is remembered. Waste is logged from the Section tab, not the capture bar | Asking "where are you today?" added friction when hopping sections, and the app didn't need it; fewer things on the home screen (first real use, 25 Nov 2026) |
| 49 | Techniques: built-in names, aliases and method templates are added once (like Bench) and are then the chef's to change. Links from steps and prep notes aren't stored: technique words are found when shown (whole words, usual endings, longest first, not inside a multi-word ingredient or component name such as "tom puree"), so "used in" and "techniques applied" are always current. A template is method lines, read by the step reader when applied and added to the end of the method; built-in templates are written so every line reads completely. Notes sorted into a technique are attempt notes linked to it | Shipped names make linking work from day one; working links out avoids keeping two copies in step |
| 50 | Scheduler v1 plans for one chef. It's worked out from today's sheet each time it's shown, from the start of today's shift (from now with no shift set), and never stored. Each unticked item with a ready recipe is a job: its parts in order, times on the upper end, not yet scaled by quantity. Ready by the item's service, else the first service you work today still to come, else the end of the shift. Never two hands-on parts at once, up to two check-in parts alongside, left-alone parts unlimited. Equipment clashes only at different settings. A part that can't be left waits until after a service window if it can still be ready in time; otherwise it goes in the window, flagged "needs cover". A warm hold ("hold warm max 2 hrs") stops it being made earlier than that. Day-before parts of tomorrow's sheet go in today's plan; today's items skip them, noted as started yesterday. Drafts and items with no recipe sit beside the plan | SPEC's greedy baseline, kept simple and explainable; quantity scaling and learned times come with prep mode (Phase 9) |
| 51 | Prep mode records each step started today in `partRuns` (schema v6): start, done, interrupted, in a service window. The plan still isn't stored: prep mode works out the queue from the day's plan and these records. Being behind only re-orders unstarted steps when a job would miss its ready-by time; otherwise it says "X min behind"; during service nothing is re-ordered and there's no countdown. Done on a hands-on step starts the next hands-on one; a step left to cook is "Started" and runs in a strip until Done. A job's last step done ticks its sheet item. Learned times: keyed by recipe and step wording (`component|step text|part`); interrupted, service-window and sub-30-second (mis-tap) timings don't count; at least 3 timings; recency-weighted median (half-life 30 days); with different batch sizes, setup plus a per-batch rate. Hands-on times are the chef's (any kitchen); times for things left in equipment stay with the kitchen. A learned time replaces the written one in the plan; the recipe's written time is never changed | SM1–SM4; a plan that holds still unless it matters; learning that one bad day can't wreck |
| 52 | Food safety. Allergen sub-types live in the same lists as the 14, as "allergen:sub-type" ("tree-nuts:hazelnut"). Allergens are worked out, never stored: basic ingredients' own, bought-in ingredients' product, through every component, for the variation in use, each with where it comes from. A line uses its chosen product, else this kitchen's only product for that ingredient, else it's "not confirmed"; a product only counts once its label is checked (entering its allergens counts; "Checked today" for one with none). Never "allergen-free" while anything is unconfirmed. A product change says which recipes it re-checked. Shelf life is a house rule per kitchen, for a component or its type (the component's wins), written as the kitchen writes it ("3 days"; a bare number is days); no rule, no use-by. "Made" creates a batch and shows a day-dot label with the chef's initials (a setting) and allergens. Targets for cooling, hot holding and reheating are house rules; without one, steps show England's legal limit as a reminder to check the kitchen's pack. Reheating is a critical point | FS1–FS3, FS5; the app records what the chef enters and never invents a safety value |
| 53 | Section admin. Costs are worked out, never stored, from product prices (this kitchen's chosen or only product, else the first with a price): through every component, with an ingredient's yield loss; a dish per portion from each component's amount per portion. GP is from the menu price without VAT (20%), against the target on that menu; what couldn't be costed is listed. Counts are per section and day (`stockCounts`); stock value is from the latest count; draft orders are ingredients below par in whole packs, grouped by supplier, sent by the chef (Mep never orders). Writing the next sheet tops up components below par ("top up to 2l"), never twice. Opening and closing checklists are per section; each day's ticks are a `checklistRuns` row (schema v7); official temperature records stay in the kitchen's system. "Also used elsewhere" notes the same component or a shared ingredient on other dishes on menus on now, with at most a prompt (heads-up on tomorrow's sheet, or a reminder). The allergen matrix and weekly report print or save as PDF through the browser; the matrix is headed as a working copy. Goal and par suggestions are only suggestions (par: short at 3+ counts → +25%; over-prep waste twice → −20%). Waste entries are matched to a component or ingredient by name, for costing | A1–A9, G1: the chef's working figures without a second system; nothing that looks like the kitchen's official records |
| 54 | Less on each page (after first real use, 25 Nov 2026). Money has its own screen (Section → Money: GP by menu, prices to add, recipe costs, this week's stock value and waste); recipe, dish and menu pages, the waste log and the count show no costs or GP (draft orders keep their estimate). The Section tab is in two groups: On shift (section lists, checks, batches and labels, waste log) and Admin (count, orders, Money, goal, report). Recipe and dish pages open on what you cook from (recipe: yield, ingredients, method, Made; dish: where it's from, components, add to sheet with allergens, portions, plating); the rest folds under "More about this recipe/dish". A dish has a kitchen (schema v8, `Dish.kitchenId`, null = the chef's own): new dishes take the kitchen they're written in; older ones take their first menu's kitchen, else their components' house recipes', else none. Names stay as the menu writes them ("Steak"); where it's from shows underneath and in search, and the library filters by it (each kitchen with something in the book, then Mine, then All; starts on the current kitchen). Names written as "Steak (Dumbleton, 2026)" can be tidied once from the library, with undo: the brackets go and the kitchen is recorded (a component with one variation becomes that kitchen's house recipe); the year isn't kept | The app was getting clunky with every phase adding to the same pages; a name shouldn't have to carry data the app already has |
| 55 | Read by default, edit on request. Recipes, dishes, menus and techniques open in a reading view with no fields; Edit (top right) switches the same page into edit mode with `?edit=1` in the address, so Back leaves edit mode; Done returns. New things, and recipes with nothing written, open in edit mode. In edit mode the ingredients and method boxes show what Mep read directly underneath. On a menu, tapping a dish opens the dish; course, price, target GP and who makes what are set from the menu's edit mode, with copy, launch and delete. Settings, kitchen settings and the ingredient page stay forms | Every page opened as a form, so reading a recipe on shift meant scrolling past editors (feel pass, 26 Nov 2026) |
| 56 | The capture bar shows on Today, Plan, Section and the inbox only, not in the library, settings, kitchen settings, prep mode or any edit mode (replaces "on every main screen"). Where it shows, it folds away while scrolling down and comes back on scrolling up or stopping; with reduced motion it just shows and hides | With the top bar and tab bar it took about a fifth of the screen, on screens where nothing is captured |
| 57 | A menu says when it's served: days of the week and the kitchen's services (schema v9, `Menu.days`, `Menu.serviceIds`; empty = every day / every service; older menus become every day). Its status is whether it's in use: "Current" (was "On now"), coming up, past. Menus are labelled by when they're served ("Sundays · Lunch"); the library opens on a current menu served today; ••• → Menus lists today's. Start and end dates are optional and folded away: in practice a new menu takes over from the old one (copy, then launch). New menus are asked their days and services as they're made | A Sunday lunch menu showed as "on now" all week; dates are rarely known, days and services always are (Louis, 26 Nov 2026) |
| 58 | In the library's Dishes view, one control says what's shown: the heading opens "Show", listing each kitchen (the current one first, then kitchens you've worked in) with its menus and "All [kitchen] dishes", then "My own dishes" and "Everything" (the whole library, each dish saying where it's from). There's no separate where-from filter on dishes; Filter keeps tags, collections and (on a menu) section. Where-from stays a filter on Components. The choice is remembered; with none, it opens on a current menu served today | A menu picker and a where-from filter answered the same question and could disagree ("All" still showed one kitchen's menu) |
